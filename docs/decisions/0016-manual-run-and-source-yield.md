# 0016 — 手动运行、不限时间窗与信源产出率（M9）

- 状态：已接受
- 日期：2026-11-05
- 修订：ADR 0005（`--limit` 口径不变，新增不限时间窗模式）

## 背景

2026-11-05 的定时运行 07:01 启动，抓取到一半时电脑睡眠，10:38 唤醒后继续跑。固定时间自动运行与用户的使用节奏不匹配。用户希望：

- 改为启动服务后手动触发每天的过滤，同时保留切回每天固定时间自动运行的开关；
- 时间窗可以不限，只去重，因为要补的内容很多；
- 信源太多、信息冲击大，但不想逐个人工筛选信源。

## 决策

### 1. 运行方式开关 = 定时任务是否已安装

- 不新增配置项：安装了 LaunchAgent（`com.secondbrain.run`）就是"每天 HH:MM 自动"，没安装就是"手动"。
- `/ops` 显示当前模式。时间从 plist 读取；只有 plist 存在时才调用 `launchctl list` 判断是否已加载。
- 两个按钮，切换前都需要确认（hx-confirm）：
  - "改为手动"：相当于 `sb schedule uninstall`。如果检测到有运行在进行（run.lock 被占用，或 Web 运行任务未结束），**直接拒绝**，因为 unload 会终止该运行。这是两种方案中更简单的一种。
  - "开启每日自动"：相当于 `sb schedule install`，可以填写时间，默认 07:00，并显示该时间换算成 UTC 后是否落在 DeepSeek 高峰。
- `schedule.status / install / uninstall` 由 CLI 与 Web 共用。
- 环境变量 `SB_LAUNCH_AGENTS_DIR` 可以覆盖 LaunchAgents 目录。测试中自动指向临时目录，从而不会读写真实的 `~/Library/LaunchAgents`，也不会执行真实的 launchctl。

### 2. 首页"开始今日过滤"

- 判断"今天是否已运行"的依据：今天是否已有 digest（`MAX(digests.date)` 等于本地今天）。这是现有数据里最直接的记录。
  - 一次没有产生任何 digest 行的运行（例如没有新条目）不算"已运行"，按钮会继续显示。
- 三种状态：
  - **todo**：显示按钮（可勾选"不限时间窗"）和一行说明（大致耗时、费用区间）。点击后启动与 `/ops`"立即运行"相同的后台任务。首页每 2 秒轮询进度，完成后通过 `HX-Refresh` 整页刷新。
  - **running**：Web 任务未结束，或 run.lock 被占用（包括 CLI 与定时任务）。只显示状态，不能再次启动。
  - **done**：显示"再运行一次"的小入口，跳到 `/ops`。同一天多次运行本来就共享预算。

### 3. 不限时间窗（只去重）

- 入口：`sb run --all-time`，以及首页和 `/ops` 上的勾选项。
- `collect` 不按 `max_age_days` 截断：所有条目都当作常规条目（backfill 信源这一次也不进回补池）。每个信源仍按 `run.fetch_limit` 取最新 N 条再去重，ADR 0005 的口径不变。
- L0 对本次的新条目使用 `ignore_age=True`。以前已被 L0 以"超出时间窗"排除的条目不会被重新考虑。
- 预算、lane 和费用上限不变。
- **`run.max_cost_usd` 的现有逻辑**：只在调用 L2 之前检查一次，条件是"已花费（主要是 L1）+ L2 预估 > 上限"。超限时 L1 结果已经写入，但本次不调用 L2、不分级，CLI 返回 1，Web 任务显示失败和原因。下次运行时已粗筛的条目不会重复花 L1 费用，L2 会再按上限检查。L1 本身没有预先的费用上限，只能用 `sb run --limit N` 限制送入 L1 的条数。
- **首次运行的预期量级**（按 example 配置）：
  - 39 个有效信源（启用且不是 needs_scraper）× `fetch_limit` 20 = **最多约 780 条新条目**。实际会更少：已入库的会被去重，很多 feed 不足 20 条。作为参考，M1 首次带时间窗抓取时新增 216 条。
  - L1（flash，每条约 4.6k 字符输入）约 **$0.5（高峰）/ $0.25（非高峰）**；L2 选 15 条约 **$0.1（高峰）**。
  - 高峰时段第一次运行时，L1 已花费加上 L2 预估可能超过默认上限 $0.5，于是 L2 被跳过（见上一条）。建议首次不限时间窗的运行放在非高峰时段，或者临时调高 `run.max_cost_usd`，或者用 `--limit` 分几次跑。
  - 耗时主要花在抓取正文（每个 host 限速 1 秒）和 L1 批次上，预计 10–20 分钟。

### 4. 速览与归档默认折叠

- 首页（`/history` 的日期链接打开的也是首页模板）的速览与归档两栏，用 `<details>` 折叠，标题为"速览（N 条）""归档（N 条）"。不依赖 JS。
- 折叠区域内每条都有反馈按钮，HTMX 照常工作。
- 前排各栏保持展开。

### 5. 信源产出率

- 统计窗口为近 `personalize.yield_window_days`（默认 30）天，按条目的 `fetched_at` 计。统计项：
  - **入库数**；
  - **精读数**：有 L2 评估，即通过 L1 被选中精读，这是现有数据最自然的口径；
  - **前排数**：出现在 must_read / worth_it / refresher / serendipity 中；
  - 当前反馈的正 / 负数。
- **低产出**需要同时满足四个条件：
  - 信源仍启用；
  - 最早入库时间早于窗口起点（新加入、历史不足一个窗口的不标记）；
  - 窗口内入库 ≥ `personalize.low_yield_min_items`（默认 5）；
  - 前排数为 0。
- `/sources` 中低产出的信源显示"低产出，建议停用"，旁边是一键停用按钮（复用 toggle）。`sb sources tune` 也会列出低产出信源；它是只读的，停用仍通过 `/sources` 或修改配置文件完成。

## 后果

- 正面：
  - 用户在合适的时候手动运行，不会再出现睡眠打断的定时运行；
  - 可以一次性补历史内容；
  - 低产出信源有数据支撑的停用建议。
- 负面：
  - 不限时间窗的首次运行费用接近默认上限，可能被跳过 L2；
  - "今天是否已运行"以 digest 为准，没有产出的运行不算；
  - 正在进行的定时运行只有在它使用 run.lock（M7 起的代码）时才能被检测到。
